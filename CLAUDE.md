# CLAUDE.md

Guidance for Claude Code (or any agent) working in this repository.

## Project purpose

Groundtruth demonstrates that RAG retrieval changes can be evaluated
objectively against a versioned golden dataset, rather than judged by
eyeballing a handful of queries. It compares retrieval configurations,
computes Recall@K / MRR / nDCG overall and per category, gates regressions
in CI, and explains *why* specific queries fail. It is a synthetic,
weekend-scale project built to demonstrate evaluation engineering — not a
production legal search system.

## Architecture

```
experiments/         YAML experiment configs - the ONLY place retrieval configs are defined
data/synthetic/      fictional corpus + golden set (deterministic; the CI gate uses this)
data/real_world/     small public-domain benchmark (generalization check; never gated)
scripts/             dataset generation + validation (build_dataset, validate_dataset, build_real_world)
src/retrieval/       configs.py (loads experiments/*.yaml) + retriever.py
src/evaluation/      metrics, evaluate, run, compare, statistics, error_analysis, report, regression_gate
src/generation/      generate.py - kept fully separate from retrieval metrics
src/api/             FastAPI RAG demo (retrieval and generation reported separately)
tests/               unit/ integration/ evaluation/ + test_regression_gate.py (the gate entry point)
reports/             baseline_metrics.json (approved CI baseline) + generated reports
runs/                local timestamped experiment runs (git-ignored, never hand-edited)
```

## Important commands

```bash
# One-time dataset build (only re-run if intentionally changing the dataset):
python scripts/build_dataset.py && python scripts/validate_dataset.py

pytest                                    # everything (must be green)
pytest -m unit | -m integration | -m evaluation
python -m src.evaluation.evaluate         # all configs -> reports/ (comparison.md/csv, dashboard.html)
python -m src.evaluation.evaluate --dataset real_world     # -> reports/real_world/
python -m src.evaluation.run --config experiments/hybrid.yaml [--dataset real_world]   # -> runs/<ts>_<name>/
python -m src.evaluation.compare --baseline baseline --candidate hybrid   # paired bootstrap CIs
python -m src.evaluation.error_analysis [--config X] [--compare-with Y]   # failure taxonomy
uvicorn src.api.app:app --reload          # RAG demo (needs `pip install -e ".[api]"`)

# Reproduce a CI regression-gate failure on demand:
EVAL_CONFIG=broken pytest tests/test_regression_gate.py
```

## Dataset rules

- **Never modify the golden dataset merely to make an experiment pass.** If
  retrieval performs worse, that is the result — report it, don't relabel
  the data to hide it.
- `data/synthetic/` is generated by `scripts/build_dataset.py` (seeded,
  deterministic) then reviewed by `scripts/validate_dataset.py`. If you need
  new examples, extend the generator - don't hand-append one-off entries.
- `data/real_world/` holds verbatim public-domain excerpts. Never invent or
  paraphrase text there, and keep its README's sources/citations accurate.
- If existing examples must change, bump `dataset_version` in that dataset's
  `dataset_meta.json` and record the change in its README changelog. Never
  silently edit an existing example. Changing a dataset invalidates the
  approved baseline: the gate refuses to compare across dataset versions.

## Evaluation rules

- Retrieval configurations live only in `experiments/*.yaml` (loaded by
  `src/retrieval/configs.py`). Don't scatter chunk sizes or model names elsewhere.
- Never call a difference "significant"/"better" unless the paired-bootstrap
  interval excludes 0; report inconclusive results as inconclusive.
- Error-analysis labels must come from computed signals with evidence; never
  hand-write failure explanations.
- Retrieval metrics (Recall@K, MRR, nDCG) and generation metrics
  (faithfulness, answer relevance) must remain separate. Never combine them
  into one blended score — a retrieval failure and a generation failure are
  different problems with different fixes.
- Do not hardcode experiment results anywhere (README, reports, tests).
  Every number in this repo should come from an actual run of
  `src/evaluation/evaluate.py` or `error_analysis.py`.
- `reports/baseline_metrics.json` is the approved CI baseline. It is only
  ever written by `python -m src.evaluation.evaluate --approve-baseline`,
  and only after a human has reviewed and accepted the new numbers as a
  genuine improvement or intentional change — never to make a failing test
  pass.

## What should NOT be changed casually

- **Never change `REGRESSION_THRESHOLD` (default `0.01`) to hide a
  regression.** If the threshold genuinely needs to change, that's a
  reviewed decision, documented in the commit message, not a quiet edit
  made because CI was red.
- Don't add abstraction layers (`interfaces/`, `factories/`,
  `repositories/`, `services/`, `providers/`, ...). This project is
  intentionally small — a handful of understandable files, not a framework.
- Don't add LangChain/LlamaIndex or other heavy frameworks. The dependency
  list is deliberately minimal.

## How the regression gate works

`src/evaluation/regression_gate.py` exposes `check_regression(baseline,
new, threshold, baseline_dataset_version, new_dataset_version)`, comparing
Recall@10 (`PASS if new - baseline >= -threshold`). It raises for an invalid
threshold, a missing baseline, and a dataset-version mismatch. `tests/test_regression_gate.py`
has an integration test that evaluates whichever config `EVAL_CONFIG` names
(default `baseline`) against the committed `reports/baseline_metrics.json`.
Normal `pytest` runs are green. Running
`EVAL_CONFIG=broken pytest tests/test_regression_gate.py` points that same
test at the deliberately-bad `broken` config and makes it fail with a
message showing the baseline value, the new value, the drop, and the
threshold — this is the literal, reproducible demonstration that the CI
gate works.

## How experiments are represented

Every experiment is a YAML file in `experiments/` (`retrieval`, `chunking`,
`reranker`, `candidate_pool`). `configs.py` translates each into the flat dict
the retriever consumes (`chunk_size`, `chunk_overlap`, `method`, `reranker`,
`candidate_pool`, model names) and exposes them as `CONFIGS`.
`src/retrieval/retriever.py` never special-cases configs by name. Each run
via `src.evaluation.run` writes a new `runs/` directory and never overwrites
an old one.

## Reproducibility

- All randomness (dataset generation, bootstrap) is seeded.
- The optional Ragas and LLM-answer paths are untested against a live API;
  pytest and CI must never require an API key or network beyond model downloads.
- Embedding/reranker model names are configurable via `EMBEDDING_MODEL_NAME`
  / `RERANKER_MODEL_NAME` env vars (see `.env.example`), defaulting to
  small, fast sentence-transformers models.
- When changing retrieval logic in `src/retrieval/`, run
  `python -m src.evaluation.evaluate` and `pytest` before committing, and
  compare the new numbers against `reports/baseline_metrics.json` by eye
  before considering `--approve-baseline`.
