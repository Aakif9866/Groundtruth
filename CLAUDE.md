# CLAUDE.md

Guidance for Claude Code (or any agent) working in this repository.

## Project purpose

Groundtruth demonstrates that RAG retrieval changes can be evaluated
objectively against a versioned golden dataset, rather than judged by
eyeballing a handful of queries. It compares retrieval configurations,
computes Recall@K / MRR / nDCG overall and per category, gates regressions
in CI, and explains *why* specific queries fail. It is a synthetic,
weekend-scale project built to demonstrate evaluation engineering — not a
production legal search system.

## Architecture

```
data/                golden dataset + corpus (synthetic legal documents)
scripts/             one-time/rerunnable dataset generation + validation
src/retrieval/       configs.py (the ONLY place configs are defined) + retriever.py
src/evaluation/      metrics.py, evaluate.py, regression_gate.py, error_analysis.py
src/generation/      generate.py - kept fully separate from retrieval metrics
tests/               test_metrics.py, test_regression_gate.py
reports/             baseline_metrics.json (approved CI baseline) + generated reports
```

## Important commands

```bash
# One-time dataset build (only re-run if intentionally changing the dataset):
python scripts/build_dataset.py && python scripts/validate_dataset.py

pytest                                    # unit tests + regression gate (must be green)
python -m src.evaluation.evaluate         # all configs -> reports/comparison.{md,csv}
python -m src.evaluation.evaluate --config hybrid   # single config, no report written
python -m src.evaluation.error_analysis   # worst 5 queries + real failure reasons

# Reproduce a CI regression-gate failure on demand:
EVAL_CONFIG=broken pytest tests/test_regression_gate.py
```

## Dataset rules

- **Never modify the golden dataset merely to make an experiment pass.** If
  retrieval performs worse, that is the result — report it, don't relabel
  the data to hide it.
- `data/corpus.jsonl` and `data/golden_set.jsonl` are synthetic and
  generated by `scripts/build_dataset.py` (seeded, deterministic) then
  reviewed by `scripts/validate_dataset.py`. If you need new examples,
  extend the generator — don't hand-append inconsistent one-off entries.
- If existing examples must change, bump `dataset_version` in
  `data/dataset_meta.json` and record the change in `data/README.md`'s
  changelog. Never silently edit an existing example.

## Evaluation rules

- Retrieval configurations live only in `src/retrieval/configs.py`. Don't
  scatter chunk sizes or model names elsewhere.
- Retrieval metrics (Recall@K, MRR, nDCG) and generation metrics
  (faithfulness, answer relevance) must remain separate. Never combine them
  into one blended score — a retrieval failure and a generation failure are
  different problems with different fixes.
- Do not hardcode experiment results anywhere (README, reports, tests).
  Every number in this repo should come from an actual run of
  `src/evaluation/evaluate.py` or `error_analysis.py`.
- `reports/baseline_metrics.json` is the approved CI baseline. It is only
  ever written by `python -m src.evaluation.evaluate --approve-baseline`,
  and only after a human has reviewed and accepted the new numbers as a
  genuine improvement or intentional change — never to make a failing test
  pass.

## What should NOT be changed casually

- **Never change `REGRESSION_THRESHOLD` (default `0.01`) to hide a
  regression.** If the threshold genuinely needs to change, that's a
  reviewed decision, documented in the commit message, not a quiet edit
  made because CI was red.
- Don't add abstraction layers (`interfaces/`, `factories/`,
  `repositories/`, `services/`, `providers/`, ...). This project is
  intentionally small — a handful of understandable files, not a framework.
- Don't add LangChain/LlamaIndex or other heavy frameworks. The dependency
  list is deliberately minimal.

## How the regression gate works

`src/evaluation/regression_gate.py` exposes `check_regression(baseline,
new, threshold)`, comparing Recall@10 values. `tests/test_regression_gate.py`
has an integration test that evaluates whichever config `EVAL_CONFIG` names
(default `baseline`) against the committed `reports/baseline_metrics.json`.
Normal `pytest` runs are green. Running
`EVAL_CONFIG=broken pytest tests/test_regression_gate.py` points that same
test at the deliberately-bad `broken` config and makes it fail with a
message showing the baseline value, the new value, the drop, and the
threshold — this is the literal, reproducible demonstration that the CI
gate works.

## How experiments are represented

Every experiment is a named entry in `CONFIGS` (`src/retrieval/configs.py`):
`chunk_size`, `chunk_overlap`, `method` (`dense` or `hybrid`), `reranker`
(bool), and `candidate_pool` (None = full index, or an int to restrict it,
used by the deliberately-bad `broken` config). `src/retrieval/retriever.py`
reads these fields; it does not special-case configs by name anywhere in
its logic.

## Reproducibility

- All randomness in dataset generation is seeded (`SEED = 42` in
  `scripts/build_dataset.py`).
- Embedding/reranker model names are configurable via `EMBEDDING_MODEL_NAME`
  / `RERANKER_MODEL_NAME` env vars (see `.env.example`), defaulting to
  small, fast sentence-transformers models.
- When changing retrieval logic in `src/retrieval/`, run
  `python -m src.evaluation.evaluate` and `pytest` before committing, and
  compare the new numbers against `reports/baseline_metrics.json` by eye
  before considering `--approve-baseline`.
